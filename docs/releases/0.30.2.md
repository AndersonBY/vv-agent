# 0.30.2

Long DeepSeek and local tiktoken conversations no longer need to be tokenized from scratch at
every tool step when using the supported local tokenizer. Counts stay exact:
the cache keeps both ordinary and newline-terminated counts, since adding a
newline can change the last token. It never adds plain per-message counts
with a fixed overhead.

The optimization applies to vv-llm 0.8.3 or 0.8.4 with deepseek-tokenizer 0.3.0
or tiktoken 0.14.0 (cl100k and o200k).
Hosts can check eligibility with
`vv_agent.memory.incremental_token_counting_status(model)`. An unverified
version logs one WARNING per family per process. See the exact version list
and upgrade checks in [upgrading](../upgrading.md#0302).
Empty text parts, leading CR/LF, token servers and unverified dependencies
keep the original counting algorithm. tiktoken additionally requires no leading
whitespace, and o200k requires no leading `/`. Qwen and families that can
count remotely keep the original algorithm. The process cache
holds at most 4096 entries containing digests, tokenizer identities and
integers; it does not retain message bodies. The JSON fallback estimate reuses
character counts while preserving the original serialization and rounding.

New model requests reuse canonical fragments of unchanged messages. Every
record, request and boundary digest is still checked. Read-only policy checks
borrow the frozen task; callers and hooks still receive detached values.
Model routing is resolved again before dispatch so endpoint changes made after
planning still take effect.

Contract 31.0.0, record schema 1, inbox schema 3, SQL layouts and all stored
bytes stay unchanged. Both full message snapshots remain. No migration or host
API change is needed.

Tests compare token counts with the old algorithm, compare compaction and
memory decisions and complete record bytes, and load histories produced by
release tags from 0.24.0 through 0.30.1.
