# 0.24.0

Contract **27.0.0**, public API **v11**, inbox schema **3**.

## Model selection

A session's model can now change while it runs. The host pushes a
`model_selection` input; the next model call after the current batch closes
uses it, and later turns keep it until another selection or a clear
(`{"selection": None}`) restores the task's frozen model. A call already in
flight, and its retries, keep the model they were planned with, and so does
their usage.

`Runtime.model_resolver` turns a selection into a client and resolved model
config, so a session can switch backends. A selection that cannot be resolved
is rejected and the previous one stays in effect. Compaction budgets follow
the effective model's context and output limits. App Server clients use
`thread/model/select`. Details are in
[session model selection](../session-model-selection.md).

## Store boundary

Inbox schema 3 replaces schema 2, and every `input_applied` record embeds the
inbox item it consumed. 0.24.0 therefore cannot read sessions written by 0.23.x,
including finished ones. Drain sessions and copy what your product needs before
switching; see [upgrading](../upgrading.md#session-data-and-upgrades).

- PostgreSQL: the `sk_inbox.kind` check constraint gains `'model_selection'`.
  Take the current DDL from `src/vv_agent/session/postgres.py`.
- SQLite files use `user_version` 3; versions 1 and 2 are rejected.

Record schema 1, RunEvent v6 and App Server protocol v2 are unchanged. Rust
stays frozen at contract 23.0.0 / package 0.21.x.
